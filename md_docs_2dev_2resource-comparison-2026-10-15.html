Linux resource comparison — 2026-10-15

This comparison supports the bounded queue and log changes. It does not show an improvement in typical whole-app CPU or memory use. The last section records the later common-clock and X11 wait fixes; earlier tables describe the intermediate candidate and retain the unsuccessful runs.

Baseline: d3841e13d1b72f1c53240424bf80dcfe64e2e0a3, exported with git archive. Only the measurement target was added to that exported source. Candidate: the working changes based on the same commit, including the bounded IPC queue, UI log-line cap, file-tail timer, and interface changes. Both builds used Debian 13 x86-64, GCC 14.2, Qt 6.8.2, and RelWithDebInfo. Compilation finished before measurement. This was a shared cloud environment, without control over other tenants' load.

The burst scenarios are medians of three runs in alternating build order. Memory is process RSS sampled while the tested queue or widget still exists; CPU is the process CPU time for the workload, including cleanup.

The queue now retains at most 64 messages and 128 Ki UTF-16 characters, with one latest snapshot per status command. Old event notifications are discarded first when the budget is exhausted. Individual pending messages over 64 KiB in UTF-8 are discarded. The GUI log caps each displayed line at 4,096 characters; this does not shorten the underlying log file.

The fallback timer wakes less often, while the native file watcher remains enabled. These samples do not establish a CPU saving: measured CPU increased. GUI CPU corresponds to approximately 0.10% → 0.33% of one core over the sample. Short runs, scheduler noise, and /proc CPU resolution limit the conclusion. The candidate GUI used about 1.17 MiB more RSS in this run.

Before declaring resource optimization complete, compare longer repeated runs with connected real computers, input and clipboard traffic, reconnects, and sleep/wake on Windows and macOS. Profile any persistent idle regression rather than extrapolating burst savings to normal use.

Common clock and event-wait correction

Arch::time() divided an integer microsecond count by integer 1,000,000 before converting to double. It therefore returned whole seconds, despite callers using it for subsecond input timers, timeouts, and retries. It now returns std::chrono::duration<double> from the monotonic clock. This is shared by all platforms; native Windows/macOS execution is still outstanding.

The new 60 ms clock regression test fails against the unchanged baseline and passes against the candidate. Two separate X11 tests also fail against the baseline: an early-return path left m_waiting set, and a 500 ms idle wait caused 20 voluntary context switches. The candidate clears the flag and uses a 250 ms safety poll with real elapsed-time accounting and upward millisecond rounding. The idle test observed 2 voluntary context switches. A posted event wakes the pipe directly; a separate test verifies it does not wait for the safety poll.

Windows message-wait rounding was also changed so positive sub-millisecond delays do not become zero-time polls. That native implementation has not been built or executed in this Linux environment.
